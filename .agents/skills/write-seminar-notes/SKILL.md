# 세미나용 지식 기록

## 범위와 입력
사용자가 지식 기록을 요청하거나 이 스킬을 적용한 작업에서 재사용할 만한 발견이 생기면 주제별 Markdown으로 저장한다. 현재 대화의 근거와 관련 코드·로그·설계 문서를 읽는다. 단순 실행 로그 전체를 복제하기보다 왜 그런 구조인지, 어떻게 동작하는지, 실험이 무엇을 검증하는지 설명한다.

[현행 연구 목표](../../../docs/README.md#현행-연구-목표와-성능-정의)와 [두 트랙 경계](../../../docs/research/two-track-scope.md)를 따른다. 현재 PEL 작업의 집계는 고정한다. 지식을 설명하는 그림이나 수식이 집계 변경 또는 미구현 통합을 실제 동작처럼 보여주지 않도록 한다. 기록을 위해 새 학습·구현·외부 게시를 시작하지 않는다.

## 저장과 갱신
사용자가 지정한 경로를 우선한다. 기본은 `docs/seminar/YYYY-MM-DD_주제.md`이며 날짜는 기록일이다. 실험일과 코드 기준일은 본문에 별도로 남긴다. UTF-8로 저장하고 한글 주제명은 보존한다. Windows 금지 문자와 끝의 공백·마침표는 피한다.

기존 노트와 docs/architecture/, docs/research/에서 같은 주제를 찾는다. 같은 설명의 갱신이면 기존 파일을 수정하고 갱신일·변경 이유를 기록한다. 다른 주제나 별도 비교라면 새 파일로 연결한다. 근거 원본은 기존 설계·연구 문서에 두고 세미나 노트는 발표용 설명과 링크를 제공한다. `docs/seminar/README.md`에 실제 저장한 노트만 제목·핵심 질문·날짜와 함께 등록한다. 다른 위치를 지정한 경우 그 위치의 기존 색인을 따른다.

[노트 템플릿](assets/seminar-note-template.md)을 출발점으로 쓰되 해당 주제에 없는 절은 제거한다. 빈 절, 작성 안내, 가짜 데이터나 예시 수식을 완성된 발표 자료에 남기지 않는다.

## 발표용 내용
- 제목 바로 아래 최상단에 핵심 질문을 callout 안의 bullet point로 나열한다. Markdown에서는 `> [!NOTE] 핵심 질문`과 인용된 bullet을 사용한다. `/callout` 블록에 대응하는 표현이며 단순 `/callout` 문자열을 본문에 남기지 않는다.
- callout 다음에 기록일·갱신일·관련 트랙·범위·코드 기준·근거 요약을 유지한다.
- 중요 개념은 정의·역할·차이를 담은 개조식 bullet로 작성한다. `~다`로 끝나는 서술문 대신 `논리적 학습 주체`, `로컬 계산`, `상태 유지`처럼 명사형 또는 짧은 구로 표현한다.
- 전제와 필요한 배경을 설명한 뒤 전체 구조, 세부 계산, 실험 질문과 관찰로 이어간다.
- 구현 사실, 로그 관찰, 원인 가설, 개선 제안, 미확인을 명시적으로 구분한다. 원본 방법론과 현재 이식 구현도 구분한다.
- 수치에는 dataset·scene/event·집계·seed·평가 정책과 단위를 함께 표시한다. 필요하면 기존 결과표에 연결하며 발표 문서 작성만을 이유로 결과표 이미지를 추가 생성하지 않는다.
- 세미나 발표 포인트와 예상 질문·답변 절은 작성하지 않는다. 근거와 관련 자료, 확인 기록은 유지한다.

## Mermaid 도식
아키텍처·데이터 흐름·실험 절차가 주제에 있으면 Markdown의 mermaid fenced code block으로 작성한다. 구조/분기에는 flowchart, 시간 순서 통신에는 sequenceDiagram 등 의미에 맞는 형식을 쓴다. 의미 없는 필수 그림을 채우지 않는다.

노드 ID는 짧은 영문으로, 한글 label은 큰따옴표로 감싼다. 화살표가 데이터, gradient, 가중치 전달 중 무엇을 뜻하는지 label 또는 범례로 표시한다. 필요하면 shape와 trainable/frozen, shared/local 경계를 적는다. 복잡한 그림은 전체/로컬 계산/실험 절차로 나눈다. Mermaid label에 LaTeX 수식 렌더링을 전제하지 않고 수식은 아래 본문에 별도로 적는다.

노드 label은 `주제: 설명` 형태를 사용하지 않는다. 주제만 적거나 `주제<br/>(설명)`처럼 줄바꿈 후 괄호 안에 짧은 설명을 적는다. 렌더 시 `AAA\n(BBB)`의 두 줄 형태를 의도하며 flowchart에는 `<br/>`를 사용한다. 긴 설명과 실행 순서의 세부 의미는 본문 또는 범례로 옮긴다.

현재 구현과 제안 구조는 별도 그림이나 명확한 제안 표기로 구분한다. event 로컬 단일 이벤트와 scene 실제 배치 구성을 혼동하지 않고 클라이언트 간 원본 영상 이동을 가정하지 않는다.

## LaTeX 수식
짧은 수식은 `$...$`, 독립 수식은 `$$` 블록에 작성한다. 설명 문장 밖의 LaTeX를 일반 코드 블록에 넣지 않는다. 변수·인덱스·shape·단위·정규화 축을 정의하고 평균, pooling, mask, detach와 gradient 의미를 설명한다. 유도가 필요하면 aligned 환경으로 단계와 가정을 적는다.

각 기호의 설명은 수식 아래에 개조식 bullet로 유지한다. 모든 새 기호를 정의하고 `참여 클라이언트 수`, `정상 loader 배치 수`, `합이 1인 집계 계수`처럼 짧은 명사형으로 작성한다.

수식은 근거 코드/원문과 맞아야 한다. 단순화했다면 생략한 부분과 적용 조건을 밝힌다. 개념 예시 식을 실제 구현 수식으로 오해하게 쓰지 않는다. 문서 뷰어가 Mermaid/수학 렌더링을 지원하지 않아도 원본 문법을 보존하며 실제 렌더 확인 여부를 구분한다.

## 검증과 완료 보고
코드·출처와 노트의 모듈 위치, 화살표, 연산 순서, 변수·shape와 숫자를 대조한다. fenced block과 수식 delimiter 균형, 로컬 링크·색인·파일명 및 한글 인코딩을 확인한다. 가능한 뷰어로 Mermaid와 수식을 확인하되 도구가 없으면 정적 확인과 렌더 미검증을 구분해 보고한다. 관련 근거·열린 문제와 저장 파일 링크를 완료 보고에 포함한다.

## 공식 용어와 축약 표현 규칙
문서를 생성·정리·갱신할 때 [공통 용어 지침](../../../docs/writing-guidelines.md)을 반드시 따른다. 논문·명세·공식 문서에서 확인한 공식 용어와 공식 약어만 사용한다. 어시스턴트가 자체적으로 만든 축약 표현은 사용하지 않는다. 공식 명칭이 없는 실험·변형은 대상·방법·조건·목적이 이해되도록 풀어서 쓰며, 조사 생략과 단어 나열은 의미가 분명한 경우에만 허용한다.

제목·파일명·표의 행과 열·통합표·세미나 문서·도식 label·수식 설명·완료 보고에도 동일하게 적용한다. 코드 식별자·원본 로그는 정확히 인용하되 독자용 완전한 설명을 병기한다. 기존 기계 판독 필드를 임의 변경하지 않는다. 기존 스킬의 짧은 예시보다 이 규칙이 우선하며 저장 전에 공식성·명확성을 확인한다.
